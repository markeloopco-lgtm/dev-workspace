# 人に読ませる文章の書き方・構成ガイド

ブログ・YouTube概要欄・配信告知・依頼文・ドキュメントなど、
「人に読んでもらう文章」全般に使える汎用ガイド。
プロジェクト固有の手順書ではないので、どの作業にも持ち出して使える。

## 要点（これだけで7割変わる）

1. **読者は読まない前提で書く**。流し読みされても伝わる形にする
2. **結論を最初に書く**。理由と詳細は後ろ
3. **一文一義・一段落一トピック**。1つの文/段落に1つのことだけ
4. **見出しだけ拾い読みしても話が通じる**構成にする
5. 書き終えたら**2割削る**。推敲とは削ることと見つけたり

以下、順に詳しく説明する。

---

## 1. 書く前に決める3つのこと

書き始める前に、次の3点を1行ずつメモする。これが決まっていない文章は、
どれだけ丁寧に書いても「何が言いたいのか分からない」と言われる。

| 決めること | 問い | 例（配信告知の場合） |
|---|---|---|
| 読者 | 誰が読むか。何を知っていて何を知らないか | チャンネル未登録の一見さん。キャラを知らない |
| 主旨 | 伝えたいことを**1つだけ**挙げるなら何か | 今夜21時から初見歓迎の雑談配信をやる |
| 行動 | 読み終えた読者にどうしてほしいか | リマインダー登録をしてほしい |

コツは主旨を**1つに絞る**こと。伝えたいことが3つあるなら、文章を3つに分けるか、
1つを主役にして残りを脇役に格下げする。全部を主役にすると全部が埋もれる。

## 2. 全体構成の型

構成はゼロから考えず、型に流し込む。代表的な型は3つ＋α。

### 逆ピラミッド型（迷ったらこれ）

重要な情報から順に書く。新聞記事の構成。

```
結論・最重要事項
  ↓
補足・理由
  ↓
細部・背景
```

読者がどこで離脱しても、そこまでで最重要のことは伝わっている。
ビジネス連絡・告知・報告・README はほぼこれ一択でよい。

### PREP法（意見を伝えるとき）

- **P**oint: 結論「私は〜と考える」
- **R**eason: 理由「なぜなら〜」
- **E**xample: 具体例・データ「実際に〜」
- **P**oint: 結論の再提示「だから〜」

主張→根拠→実例→念押し、の流れ。ブログの主張記事やレビューに向く。
最後にもう一度結論を書くのがポイントで、流し読みの読者を回収できる。

### SDS法（事実を報告するとき）

- **S**ummary: 全体の要約
- **D**etails: 詳細
- **S**ummary: まとめ

PREPの「意見」を「事実」に置き換えた型。ニュース・お知らせ・作業報告に向く。

### ストーリー型（共感を得たいとき）

「日常 → 事件 → 苦労 → 転機 → 変化」の順で時系列に語る。
結論を後ろに置く唯一の型で、エッセイ・体験談・自己紹介に向く。
ただし読者が最後まで読む動機（続きが気になる仕掛け）が冒頭に必要。
**情報伝達には使わない**。急ぎの用件をストーリーで書かれると読者は苛立つ。

### 型の選び方

| 目的 | 型 |
|---|---|
| 告知・連絡・報告 | 逆ピラミッド or SDS |
| 意見・提案・レビュー | PREP |
| 手順の説明 | 逆ピラミッド（先に完成形を見せてから手順） |
| 共感・ファン作り | ストーリー |

## 3. タイトル・見出し・リード

### タイトルは「読む前の読者」に向けて書く

読者はタイトルだけを見て読むかどうかを決める。中身がどれだけ良くても、
タイトルで内容と利益が伝わらなければ読まれない。

- ❌ `配信について` → 何の情報もない
- ⭕ `【今夜21時】初見歓迎の雑談配信をやります` → 日時・内容・対象が入っている

コツは3つ。**具体的に**（固有名詞・数字を入れる）、**読者の得を示す**
（読むと何が分かるのか）、**約束を守る**（中身以上に盛らない。釣りタイトルは
一度は開かれるが信頼を失い、次から開かれなくなる）。

### 見出しだけで筋が通るようにする

読者はまず見出しだけを拾い読み（スキャン）する。見出しを上から順に読んだとき
1つの要約として成立していれば、スキャンした読者にも主旨が伝わり、
興味を持った節だけ本文を読んでもらえる。

- ❌ `はじめに / 本題 / まとめ` → 見出しから内容が分からない
- ⭕ `結論：CPUでも動く / 根拠：実測で3秒だった / 手順：3ステップで設定`

### リード（冒頭2〜3行）で「読むべきか」を判断させる

本文の最初の2〜3行で「この文章は何で、読むと何が得られるか」を書く。
このガイドの冒頭3行がその例。リードで対象読者を明示すると、
読むべき人は安心して読み進め、対象外の人は時間を無駄にしない。

## 4. 段落（パラグラフ）の作り方

### 一段落一トピック

1つの段落では1つの話題だけを扱う。話題が変わったら段落を変える。
逆に、同じ話題の文が複数の段落に散っていたら1つにまとめる。

### 先頭の文に段落の要約を置く

段落の1文目（トピックセンテンス）だけを読めば段落の主旨が分かるように書く。
2文目以降は1文目の補強・具体化に徹する。段落の最後にオチを置く書き方は
流し読みに弱い。

### 長さはスマホ基準で2〜4文

いまの読者の大半はスマホで読む。PCで3行の段落はスマホで6〜8行の「壁」になる。
1段落は2〜4文、長くても100〜150字程度で区切り、段落間に空行を入れる。

## 5. 文（センテンス）の作り方

### 一文一義

1つの文には1つの内容だけを入れる。「〜で、〜だが、〜なので、〜です」と
繋がった文は、切れる場所すべてで切る。目安は**40〜60字**、長くても80字。

- ❌ 「昨日配信をしたのですが機材トラブルで音が出なくて、視聴者の方に
  ご迷惑をおかけしたので、今日は設定を見直してから配信します」（62字超・3つの内容）
- ⭕ 「昨日の配信は機材トラブルで音が出ませんでした。ご迷惑をおかけしました。
  今日は設定を見直してから配信します」（3文・各一義）

### 主語と述語を近づける

主語と述語が離れるほど読者の脳内メモリを消費する。間に挟まった修飾は
文の外に出すか、文を分ける。

- ❌ 「私は、昨夜の配信で紹介した、視聴者さんに教えてもらったツールを試した」
- ⭕ 「昨夜の配信で、視聴者さんに教えてもらったツールを紹介した。今日それを試した」

### 修飾語は「長いものを先に」

複数の修飾語が並ぶときは、長い修飾句を先、短い修飾語を後に置くと読みやすい。

- ❌ 「白い フリルがたくさんついた 衣装」→「白い」が何に係るか一瞬迷う
- ⭕ 「フリルがたくさんついた 白い 衣装」

### 能動態を基本にする

受け身は動作の主体をぼかすので、必要なとき以外は能動態で書く。

- ❌ 「設定ファイルが変更されました」（誰が？）
- ⭕ 「私が設定ファイルを変更しました」

### 二重否定を使わない

- ❌ 「知らなくはない」「できないわけではない」
- ⭕ 「少し知っている」「一応できる」

### 冗長表現を削る

意味を変えずに削れる言葉は削る。頻出パターン:

| 冗長 | 簡潔 |
|---|---|
| 〜することができる | 〜できる |
| 〜という機能 | 〜機能 |
| 〜を行う / 〜を実施する | 〜する |
| 〜のような形になります | 〜になります |
| まず最初に | まず |
| 〜だと思われます | 〜です（根拠があるなら言い切る） |
| 基本的に・一般的に（根拠なしの保険） | 削除 |

「思います」「たぶん」などのぼかし表現は、本当に不確かなときだけ使う。
保身のためのぼかしは文章全体の信頼を下げる。

### 文末に変化をつける

「〜です。〜です。〜です。」と同じ文末が3連続すると単調に響く。
体言止め・疑問形・「〜でしょう」「〜ください」などを混ぜてリズムを作る。
ただし体言止めの多用は稚拙に見えるので、アクセント程度に。

## 6. 言葉選びと表記

### 漢字は3割を目安に

漢字が多い文章は黒く・硬く見え、ひらがなが多すぎると幼く見える。
目安は**漢字3割：ひらがな7割**。特に形式的な語は開く（ひらがなにする）。

- 開く例: 「事」→こと、「物」→もの、「時」→とき、「下さい」→ください、
  「致します」→いたします、「更に」→さらに、「出来る」→できる

### 専門用語には一言添える

読者が知らない可能性のある用語は、初出時にカッコで短い説明を付ける。
「クロマキー（背景の緑色を透過させる合成技術）」のように。
説明が3行を超えるなら本文から切り出して脚注や別節にする。

### 表記を統一する

同じものを指す言葉は1つに固定する（「ユーザー/ユーザ」「サーバー/サーバ」など）。
数字は半角、単位・日時の書式も文書内で揃える。表記ゆれは内容の信頼まで下げる。

### 数字で具体化する

「たくさん」「高速」「すぐに」は人によって解釈が違う。
「23レイヤー」「3秒で応答」「今夜21時」のように数字で書けるものは数字で書く。

## 7. 視覚的な読みやすさ（レイアウト）

文章は「読む」前に「見られる」。パッと見て黒い壁に見えたら、読まれる前に閉じられる。

- **空行**: 段落間・話題の切れ目に必ず入れる
- **箇条書き**: 同種の項目が3つ以上並んだら文章をやめて箇条書きにする。
  各項目の文法構造（体言止めなら全部体言止め）を揃える
- **表**: 2つ以上のものを複数の観点で比べるときは表にする
- **図**: 構造・流れ・位置関係は文章で説明せず図にする（このリポジトリのREADMEの
  パイプライン図が好例）
- **強調（太字）**: 1画面に1〜2箇所まで。全部強調は無強調と同じ
- **1行の長さ**: 横に長すぎる行は目が行を見失う。全角35〜40字程度で折り返す

## 8. 推敲 — 書き終えてからが本番

初稿は「自分のために書いた文章」。推敲で「読者のための文章」に作り替える。

1. **寝かせる**: 最低数時間、できれば一晩置いてから読み直す。
   書いた直後は脳内補完が効いて欠陥が見えない
2. **音読する**: 声に出してつっかえる場所は、読者も目でつっかえる。
   息が続かない文は長すぎる文
3. **2割削る**: 全体の文字数を2割減らすつもりで、なくても意味が通る語・文・段落を消す。
   削って意味が変わらないなら、それは最初から不要だった
4. **読者になりきって読む**: 前提知識ゼロの人として読み、「これ何？」と
   引っかかる用語・飛躍がないか確認する
5. **実際の表示環境で見る**: スマホ向けならスマホで、配信概要欄なら実際の画面で
   プレビューして「壁」になっていないか見る
6. **他人（またはAI）に要約させる**: 要約が自分の主旨とズレていたら、
   伝わっていないのは読者ではなく文章の責任

## 9. 媒体別の勘所

### ブログ・note

- 冒頭リードで「誰向けで、読むと何が得られるか」を宣言する
- 見出しスキャンで筋が通る構成（§3）を最優先
- 1記事1テーマ。書きたいことが増えたら記事を分ける

### YouTubeタイトル・概要欄・配信告知

- タイトルは全角28字前後で切れる。**重要な語を先頭に**置く
- 概要欄は最初の2〜3行しか折りたたみ前に表示されない。
  日時・内容・ハッシュタグ級の重要情報をその2〜3行に集約する
- 毎回の定型部分（自己紹介・リンク集）はテンプレ化して下部に固定する

### SNS短文（X など）

- 1投稿1メッセージ。結論だけを書き、詳細はリンク先に逃がす
- 最初の1行が全て。タイムラインでは1行目しか読まれない前提で書く

### 技術ドキュメント・README

- 冒頭に「これは何か」「誰のためか」「どう使うか（最短の動かし方）」の3点
- 手順は箇条書き＋コピペ可能なコマンドで。散文の中に手順を埋めない
- 前提条件（バージョン・環境）を明記し、書いた日付を残す
- 実装を変えたらドキュメントも同じコミットで直す（ズレた文書は無い文書より害）

### チャット・依頼文

- 1行目に用件と依頼内容を書く。「お願いがあります」だけで改行して待たない
- 相手が Yes/No や選択肢で答えられる形まで絞ってから送る
- 期限・優先度があるなら明記する
